# ADR 0003: загрузка и очередь — V0-02

Аудио передаётся multipart в POST /api/v1/companies/{company_id}/calls.
Файл ограничен 50 MiB и 1800 секундами (настройки окружения), контейнер определяется
ffprobe по содержимому: WAV, MP3, M4A; видеодорожки отклоняются. Весь request body
ограничен лимитом файла плюс 64 KiB для multipart. Поток дополнительно проверяется
по фактическому количеству байтов. Файл пишется по UUID, исходное имя используется
только для отображения. SHA256 считается при записи. ffprobe/ffmpeg запускаются
без shell, без сетевых протоколов и с timeout.

python-multipart нужен для UploadFile, ffmpeg/ffprobe устанавливаются из Debian
в общий образ API/worker. Аудио хранится в отдельном named volume audio_data;
SQL содержит приватный object_key, который не отдаётся клиенту. Storage выделен
в отдельный модуль, пока реализованы только локальные операции с файлами.

Call, processing_run и job создаются одной транзакцией после атомарного
перемещения файла. При ошибке SQL файл удаляется; сбой cleanup логируется.
Crash между записью файла и SQL может оставить orphan-файл: удаление таких
файлов допускается только после сверки с БД, автоматической очистки пока нет.
Распределённой транзакции между FS и SQL нет.

Idempotency-Key ограничен 128 символами, уникален внутри компании. Повтор с
тем же SHA256 и employee_id возвращает прежнюю заявку, изменение данных — 409.
Идентичные файлы с разными ключами намеренно допускаются. Employee проверяется
по company_id как в API, так и составным FK в PostgreSQL.

Worker — отдельный процесс, concurrency=1, PostgreSQL FOR UPDATE SKIP LOCKED,
lease 60 секунд, heartbeat каждые lease/3. У каждой аренды новый UUID-token;
завершение возможно только с текущим token и неистёкшей арендой. При истечении
аренды задача забирается заново, максимум 3 попытки. Временные ошибки проверки
или хранилища получают ограниченную задержку 2^attempt (до 30 секунд).
При недоступной БД worker переподключается. ffmpeg выполняется вне транзакции.

ВАЖНО: V0-02 выполняет только preprocess (полное декодирование аудиодорожки).
Его job может стать completed, но call/run становятся awaiting_analysis,
stage=transcribe. Это явное промежуточное состояние, добавленное к черновому
контракту: call.completed зарезервирован для опубликованного валидного анализа.
В UI — «Запись проверена», с пояснением, что ASR/LLM ещё не подключены.
Заглушки транскрипта и вымышленные оценки не создаются.

GET /calls поддерживает limit/offset и employee_id; GET /calls/{id} — статус;
GET /calls/{id}/audio — FileResponse с Range/206 и Content-Type по проверенному
формату. Все ресурсы ищутся в рамках company_id. Ошибки используют существующий
FastAPI detail. Ручной retry, удаление звонков и переход awaiting_analysis к
настоящему/model-mock анализу — последующие этапы.

UI использует выбранную выше компанию, опрашивает статусы каждые 3 секунды,
отменяет старые запросы и не показывает записи другой компании. Ключ повторной
загрузки сохраняется до успеха, пока пользователь не меняет файл/сотрудника.
Незавершённая загрузка при переключении компании остаётся привязана к исходной.

Это только локальное демо без authentication, полноценной tenant isolation,
backups и retention. Volume down без -v сохраняет SQL и аудио.
